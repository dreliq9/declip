# Media Kernel Vertical Slice v0

**Status:** Phase 0 executable specification  
**Date:** 2026-08-24  
**Reference client:** Declip  
**Primary provider:** FFmpeg  
**Admission profile:** `kernel.basic_delivery_mp4.v1`

## 1. Purpose

This fixture is the first end-to-end proof that the architecture is real rather than a collection of documents.

It must exercise one path through:

```text
Declip authoring intent
      ↓
exact AssetRefs / StreamDescriptors
      ↓
typed CandidateDelta
      ↓
State validation + immutable commit
      ↓
typed/versioned Editorial IR
      ↓
controlled Transformation
      ↓
operation-oriented Executable IR
      ↓
TargetProfile / FFmpeg lowering
      ↓
LoweringReport
      ↓
Execution
      ↓
artifact + receipt
      ↓
Admission
```

The slice is intentionally small. It proves boundaries and guarantees before adding feature breadth.

## 2. Why these exact numbers

The output cadence is:

```text
30000/1001 frames/second
```

and audio is:

```text
48000 samples/second
```

Five video frames equal exactly 8,008 audio samples:

```text
5 * 1001/30000 seconds * 48000 = 8008 samples
```

The fixture therefore chooses total sequence lengths that are multiples of five video frames so both the CFR video boundary and audio sample boundary are exact.

No first-slice success is allowed to depend on undocumented frame/sample rounding.

## 5. FFmpeg execution profile

The first provider profile may use a stable test configuration equivalent to:

```text
container: MP4
video encoder: provider-selected H.264 implementation approved by test profile
video pixel representation: profile-declared 8-bit 4:2:0 compatible output
video cadence: 30000/1001 CFR
audio encoder: AAC or another explicitly frozen MP4 test-profile codec
audio sample rate: 48000
channels: stereo
```

The exact encoder/provider/version is recorded in the execution receipt.

Artifact byte hashes are expected to vary when the intentionally versioned encoder/toolchain changes unless a bit-exact provider profile is explicitly required. Admission checks semantic delivery properties rather than assuming every FFmpeg build emits identical compressed bytes.

## 7. Declip authoring adapter

The first Declip adapter may originate from a compatibility Project v1 object, but before State/Editorial commit it must produce exact semantics.

Responsibilities:

```text
path/locator -> exact AssetRef + content/version binding
float/decimal authoring input -> deterministic exact MediaTime
integer/legacy fps -> exact MediaRate
transition_in -> first-class Transition T1
settings/output -> OutputIntent + separate execution profile
track/clip position -> durable kernel IDs
```

`start="auto"`, if used in the Declip source fixture, must be resolved to the exact frame-139 placement before the candidate is canonical.

No probe fallback duration may appear silently.

## 8. CandidateDelta v1 — trim + ripple

The proposal removes exactly 30 frames from the end of Clip A and ripples downstream sequence placement/duration.

Trim amount:

```text
30 frames = 1001/1000 s
```

### Resulting Clip A

```text
151 - 30 = 121 frames
exact duration = 121121/30000 s
```

### Resulting Clip B placement

Transition remains 12 frames.

```text
121 - 12 = frame 109
new B1 start = 109109/30000 s
```

Clip B source-in and duration remain unchanged.

### Resulting sequence end

```text
121 + 151 - 12 = 260 frames
```

Exact time:

```text
260 * 1001/30000 = 13013/1500 s
```

Exact audio samples:

```text
260/5 * 8008 = 416416 samples
```

### Audio bed ripple policy

The same Declip ripple candidate trims M1's sequence duration to the new exact sequence end:

```text
M1 duration = 13013/1500 s
sample count = 416416
```

### Candidate operations

Semantically the candidate contains or normalizes to typed operations equivalent to:

```text
TrimClip(A1, duration=121121/30000)
MoveClip(B1, timeline_start=109109/30000)
TrimClip(M1, duration=13013/1500)
```

The ripple policy may be represented as a higher-level candidate operation if its deterministic expansion into these effects is part of the State/operation schema. The committed meaning must be the same.

## 9. Candidate preconditions

At minimum:

```text
base revision == R0
A1 exists with expected version/hash/fields
B1 exists with expected version/hash/fields
M1 exists with expected version/hash/fields
T1 exists and still binds A1 -> B1
branch head == R0
asset refs still resolve to expected content versions
```

A stale head or changed clip/transition causes explicit conflict. No silent rebase.

## 10. Candidate nonmutation proof

Before commit:

- R0 Snapshot hash is unchanged;
- branch head still points to R0;
- candidate projection may be inspected/lowered separately;
- candidate invalidation set may be estimated;
- rejecting the candidate leaves R0 and all R0 acceptance/cache facts unchanged.

This must be an executable conformance test, not only an API claim.

## 11. Candidate invalidation expectations

The candidate should demonstrate selective invalidation.

### Clip B source-domain analyses

Because B1 source-in/duration/source asset are unchanged and only sequence placement moves:

```text
source transcript:       PRESERVED
source scene analysis:   PRESERVED
source object tracking:  PRESERVED
```

### Clip A source analyses

The retained source interval remains reusable when the analysis contract is range-aware.

```text
retained A1 source range: conditionally preserved/reused
removed tail range: no longer referenced by this clip revision
```

Do not automatically invalidate the retained source analysis merely because sequence duration changed.

### Sequence/composite/render

Dirty sequence region begins at the new changed boundary and includes both old/new downstream placement according to dependency footprints.

At minimum:

```text
transition/composite around A1/B1 boundary: INVALIDATED
sequence render from changed boundary onward: INVALIDATED
M1 sequence/materialization past new end: INVALIDATED/removed
```

Exact dirty-range calculations become golden conformance data when the dependency engine is implemented.

## 13. Replay requirement

Starting from R0 and the canonical committed operation/candidate lineage:

```text

```

must produce byte-for-byte identical canonical Snapshot serialization and the same SHA-256 snapshot hash as the committed S1 fixture.

The golden S0/S1/candidate hashes are populated by the production canonical serializer at kernel-repository bootstrap and checked into conformance fixtures.

## 15. Editorial verification

S1 must pass:

- exact time normalization;
- source-range bounds;
- transition adjacency/range obligations;
- track/media-kind compatibility;
- audio-route/layout validity;
- OutputIntent validity;
- asset/version/content reference resolution;
- unknown critical-extension checks.

A deliberately altered fixture for each class must fail the corresponding conformance test.

## 16. Executable Media IR v1

The first exact FFmpeg-capable plan should be small but explicit.

Representative semantic nodes:

```text
1  SourceVideo(VideoA)
2  SourceRange(A1 source range)
3  SourceVideo(VideoB)
4  SourceRange(B1 source range)
5  TransitionDissolve(2,4, duration=12 frames)
6  SourceAudio(AudioBed)
7  SourceRange(M1 source range)
8  Gain/RouteAudio(7, unity unless fixture declares gain)
9  EncodeVideo(5, OutputIntent/profile)
10 EncodeAudio(8, OutputIntent/profile)
11 Mux(9,10, MP4 execution profile)
12 Sink(11, artifact target)
```

An implementation may split/fuse provider-neutral nodes only through declared canonicalization/optimization rules. The canonical plan hash must be based on the defined normalized Executable IR, not allocation order.

No `SilenceSource` is expected in this fixture because the audio bed supplies output audio independently of the video assets.

## 17. Type checking

Executable ports must prove or explicitly convert:

```text
video raster/rate/color
transition input compatibility
audio sample rate/layout
encoder input requirements
mux stream compatibility
```

Memory-domain moves do not alter semantic MediaType.

Any consequential pixel/sample/color/rate conversion inserted by the FFmpeg provider appears explicitly in the plan and `LoweringReport`.

## 18. Reference target/lowering result

The reference FFmpeg target profile must be selected so the expected semantic result is:

```text
overall lowering status: EXACT
unsupported semantics:   none
approximations:           none
editability-loss bake:    none
```

If the installed/tested provider cannot meet this contract, the fixture fails or selects another qualified implementation. It may not silently downgrade the expected result.

A separate negative target fixture deliberately disables native dissolve support and must produce either:

```text
BAKED_LOSS_OF_EDITABILITY
```

for an explicitly allowed bake path, or:

```text
UNSUPPORTED
```

when target policy forbids baking.

## 20. Artifact verification

Before Admission, probe the output independently of the FFmpeg process exit code.

Verify at least:

```text
MP4 structure readable
primary video decodes through
required audio decodes through
1920x1080
30000/1001 video cadence/profile semantics
260-frame intended sequence duration
48000 Hz stereo audio
416416-sample semantic audio duration before codec/container boundary treatment
A/V endpoints satisfy profile tolerance
BT.709 output metadata matches intent/lowering report
```

Codec priming/padding/container timestamp behavior must be handled by an explicit checker/profile rule, not a hidden tolerance.

## 21. Admission

Evaluate:

```text
kernel.basic_delivery_mp4.v1
```

Required dimensions:

```text
STRUCTURAL              PASS
DECODABILITY            PASS
DURATION_TIMING         PASS
FRAME_INTEGRITY         PASS
AV_SYNC                 PASS
VIDEO_MEDIA_TYPE        PASS
AUDIO_MEDIA_TYPE        PASS
COLOR_PIPELINE          PASS
PROVENANCE_COMPLETENESS PASS
DELIVERY_PROFILE        PASS
```

Dimensions outside the first profile are `NOT_APPLICABLE`, not silently PASS.

Only Admission creates the `AcceptanceRecord`.

## 22. Negative end-to-end cases

The conformance suite must include at least:

1. stale candidate base/head -> no R1 publication;
2. A1 source range beyond asset -> Editorial rejection;
3. transition longer than adjacent clip -> rejection;
4. unknown critical Editorial extension -> blocked;
5. provider missing required exact semantic -> lowering `UNSUPPORTED` rather than omission;
6. forced bake target -> explicit `BAKED_LOSS_OF_EDITABILITY`;
7. artifact truncated after render -> Execution may have succeeded but Admission rejects;
8. wrong raster/rate/audio layout -> Admission rejects;
9. artifact byte mutation -> prior acceptance cannot transfer;
10. same R1 replay from canonical operation lineage -> identical S1 bytes/hash.

## 23. Golden fixture data that must be checked into the kernel repo

Once the canonical schemas are implemented, commit a machine-readable fixture bundle containing:

```text
synthetic source generation recipe

R0 canonical bytes/hash
candidate canonical bytes/hash
R1 canonical bytes/hash
Editorial IR canonical bytes/hash

```

Do not hand-author hash strings before the production encoder exists. Generate them once through the canonical implementation, cross-check against an independent reference encoder, then freeze them as conformance fixtures.

## 24. Success condition

The first Media Kernel milestone is complete only when:

> **A Declip-originated exact trim+ripple proposal can remain nonmutating as a candidate, atomically become immutable Revision R1, replay to the same canonical State hash, project into typed Editorial IR, lower into an exact provider-neutral executable plan, render through FFmpeg with no silent semantic loss, emit a complete receipt, and receive an independently reproducible `kernel.basic_delivery_mp4.v1` AcceptanceRecord.**

Everything else in early construction is subordinate to proving this chain.
